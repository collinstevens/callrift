# ASP.NET Core source coverage

Source-only mode combines C# files into one compilation with BCL references. It does not evaluate ASP.NET Core's project references, shared-source includes, framework defines, source generators, Razor compilation, or runtime framework conventions. Package and template inputs produce unresolved calls and parse diagnostics. Application fixtures remain included; assertion test projects are excluded using project evidence.

The accepted JavaScript task-completion pair preserves these diagnostics and explicit depth omissions. Reflection is represented by the visible calls to reflection APIs; inferred runtime reflection targets and Native AOT execution are not claimed. Property bodies and generated serializer implementations are not followed.

A separate, unaccepted authentication-scheme candidate demonstrates cross-project type shadowing. At `26e9547de9301d6da2aa0f3a1a52eca6350060c5`, `Utf8HashLookup.GetCaseSensitiveHashCode` constructs an unqualified `HashCode`, invokes `AddBytes`, and invokes `ToHashCode`. The single source compilation binds the constructor and `ToHashCode` to the global shim in `src/Shared/HashCode.cs`, even though the SignalR Core project does not include that shim. `AddBytes` becomes unresolved. This candidate remains outside the accepted manifest; reducing depth would not establish correct binding.

The [CTS-disposal pair](../reviews/aspnetcore-stream-cts-disposal.md) originally exposed the [generic caller substitution issue](generic-context.md). A dictionary keyed by `ModelMetadata` incorrectly reached a comparer for `TagHelperAttribute`. The current implementation preserves both dictionary arguments on both pins and excludes that incompatible comparer. The pair's focused view shows only the new disposal beneath the duplicate-invocation guard; the existing `finally` disposal remains conditional on successful registration.

Its automatic view still contains 1,201 roots. Possible `ToString` implementations, interface calls, stored callbacks, and endpoint registration connect distant application fixtures to SignalR in the conservative graph. For example, an MVC sample description lookup reaches `AuthorizeAttribute.ToString`, then debugger enumeration helpers, OWIN feature callbacks, `HttpResponse` disposal callbacks, and possible endpoint implementations. Callback ancestry and possible dispatch remain explicit. The analysis does not propagate the actual description value, registered services, or callback invocation through that path. These roots are affected entries in a partial graph, not proven runtime entry points. Every reported root has a graph witness to the edited method; that check does not establish runtime feasibility or close receiver-flow limitations.

Historical MSBuild materialization currently rejects symlinks and gitlinks. Both the JavaScript task pair and CTS-disposal pair fail explicit restored trials on `src/submodules/MessagePack-CSharp`. Their source results are not fallbacks presented as restored analysis. Supported project materialization and actual cross-platform repeats remain separate requirements.
